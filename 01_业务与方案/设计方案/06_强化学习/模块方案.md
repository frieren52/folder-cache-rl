# 06 强化学习模块方案

## 1. 目标

06 加载 05 交付的监督 Actor，在有限通道、3% 字节容量和固定 LRU 环境中训练 Critic，并用候选优势继续更新 Actor。05 负责召回未来可能访问的对象，06 负责决定哪些候选值得现在预取以及何时停止。字节命中率是主指标，读取次数命中率和执行副作用同时受控。

## 2. 决策环境

首版环境配置如下：

| 项目 | 配置 |
| --- | --- |
| 决策周期 | 10 秒，包含状态构造、模型推理和动作生成 |
| 缓存容量 | 目录快照总字节数的 3% |
| 淘汰算法 | 固定 LRU |
| 方法验证主环境 | 30 通道，每通道 200 MiB/s，无额外固定准备时间 |
| 真实约束参考 | 10 通道，每通道 200 MiB/s，不用于掩盖资源瓶颈 |
| 上限诊断 | 60 通道，每通道 200 MiB/s，仅在 30 通道可训练性检查失败时使用 |
| 排队方式 | 需求取回与预取共享中央 FIFO |
| 每步预取上限 | 环境超参数，首轮默认 2 个 |

环境参数统一从配置加载并绑定环境版本；参数变化后不得复用旧快照、Replay 或 Critic。30 通道用于验证强化学习方法，10 通道保留为真实资源参考，60 通道只在 30 通道可训练性不足时作上限诊断。

每个决策时刻先更新持久历史索引：dirty 和 Actor 上下文立即刷新，近 1 小时活跃对象最多 5 分钟刷新一次，1～24 小时活跃对象最多 1 小时刷新一次，跨过 1 小时边界时立即刷新，超过 24 小时则删除。各来源按确定性到期时间合并去重后批量调用 04，只有该流程可以增加 `history_revision`。

随后执行 Actor，静态、历史两路各取 Top-256，合并为最多 512 个自然候选。06 先 Mask 已缓存、排队/在途、超大、无效、按当前 FIFO 与通道下界可确定一小时内无法完成、晚于计分终点或处于末尾结算区的对象，再仅对剩余候选按当前 `t` 临时调用 04 并计算重排和 Critic 特征；临时结果不回写持久索引。轨迹分别保存 `retrieval_history_score`、`retrieval_fusion_score`、`current_history_score`、`current_fusion_score`、`history_revision` 和 `candidate_as_of_time`。需求取回与预取共享 FIFO 和通道；对象完整取回后才进入 LRU 缓存。

## 3. 强化学习过程

```text
05 监督 Actor + 03/04 冻结产物 + 真实访问流
→ 连续回放、生成候选并执行策略
→ 相对无预取环境结算双命中差分奖励
→ 训练两套独立在线 Critic 及各自 Target
→ 用候选优势更新 Actor，并以 05 监督损失锚定
→ Actor 更新后重新生成候选轨迹
→ 验证并发布检查点与报告
```

策略环境与无预取环境从相同快照和请求流开始并独立推进。奖励为 `0.8 × 归一化字节命中差分 + 0.2 × 归一化读取次数命中差分`；等待、额外读取、污染和通道占用单独记账。训练使用两套独立 Critic、Clipped Double Q、Target 网络、6-step 回报和 Huber Loss，Replay 以可确定性重建的完整宏步为单位。

统一策略路由如下；所有路由共用同一候选、Mask、LRU、FIFO 和事件环境：

| 路由 | 作用 |
| --- | --- |
| `no_prefetch` | 无主动预取，对应 02 按需 LRU 基线 |
| `simple_greedy` | 按“完成后访问概率 × 对象字节数”选择合法候选 |
| `critic` | 冻结监督 Actor，只使用 Critic 选择 |
| `actor_critic` | 使用强化 Actor 及其绑定的 Critic |

Critic 只有在候选价值严格大于 STOP 时才选择候选，同分优先 STOP。每宏步最大预取数由环境超参数控制，首轮默认 2；策略仍可在选择 0 个或 1 个后 STOP。

## 4. 交付接口

```text
06_强化学习/
├── data/
│   ├── replay_manifest.json
│   └── versions/<版本>/（宏步与环境快照）
└── outputs/
    ├── ckpt/trained/（Actor 与 Critic）
    ├── reports/validation_report.json
    └── rl_artifact_manifest.json
```

Replay、检查点和报告必须绑定 Actor、03/04、对象主表、访问事件、环境配置及文件 SHA256。强化 Actor 保持 05 输入输出接口不变；不同通道场景使用独立版本和报告。

## 5. 验收

1. **能否跑通：** 在 Docker 中完成候选生成、环境回放、策略路由、Replay、Critic 训练、Actor 更新、检查点加载和评价的端到端流程；运行结果可复现且无硬约束错误。
2. **测试集效果：** 使用 6 月 19—23 日训练并冻结策略后，只在 6 月 24 日测试一次；在 30 通道环境中对比无预取和简单贪心，报告字节命中率、读取次数命中率及等待、额外读取、污染等副作用，同时给出 10 通道参考结果。无论 RL 有效或无效，都保存并如实报告结果。

环境状态、候选特征、Critic 结构、奖励公式、Replay 模式、训练步骤和验收口径见[详细设计](详细设计.md)。
